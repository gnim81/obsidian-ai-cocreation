# GUIDE

> The vault's two purposes: **① co-write with AI** (AI can write inside `03-Projects/`); **② serve as knowledge input for AI tools** (vault-wide read-only retrieval).
> Permissions, the state machine, and directory semantics are declared to the AI in the root `CLAUDE.md`; this manual is for humans.

## 1. First-time setup (once, ~10 minutes)

### 1.1 Open the vault in Obsidian

> Init first: run `bash init-vault.sh` at the vault root (fills MCP paths automatically; optional `--areas "AreaA,AreaB"` for custom areas).

1. Obsidian → "Open folder as vault" → select your initialized vault directory.
2. When prompted to trust the author and enable plugins, choose **trust** (community plugins won't run otherwise).

### 1.2 Enable the core Templates plugin

- Settings → Core plugins → enable **Templates**.
- The template folder is preconfigured to `00-System/templates` (via `.obsidian/templates.json`); verify under Settings → Templates if you like.
- What the templates are for now: `tpl-source` (manual source capture), `tpl-note-card` (cards), `tpl-draft` (hand-written drafts). Project skeletons (`_brief/challenges/journal`) are generated by the script — no manual templating needed.

### 1.3 Community plugins (optional)

Settings → Community plugins → turn off Restricted mode → Browse:

| Plugin | Necessity | Purpose |
|---|---|---|
| **Vault Operator** | optional | Governs **AI writes going through Obsidian** (enforces `.obsidian-agentignore` / `.obsidian-agentprotected`) + shadow snapshots; **cannot see direct file writes by external AI tools** (empirically tested — the shadow repo records no external changes). Skippable when external tools are your main method. |
| **Kanban Bases View** (or similar) | optional | Drag cards across statuses on the co-writing board |
| **Claudian** | optional | In-Obsidian AI with word-level diff editing; **the primary method is external AI tools (§5.2)** — enable only if window-switching annoys you (trade-offs in §5.3) |
| **Obsidian Git** | optional | GUI commits; **keep auto-commit OFF**, commit manually |

> Plugin names follow the community marketplace. **With external AI tools as the primary method, no community plugin is required** — the hard boundary is MCP (§5.2), and snapshots/undo are provided by manual git commits (§1.4). Vault Operator only becomes valuable if you use AI plugins inside Obsidian.

### 1.4 Git habits (the vault ships initialized)

- **Manual commits, cadence = end of a co-writing round**:

```bash
cd /path/to/your/vault
git add -A && git commit -m "co-writing: lesson-3 v2 done"
```

- **Never enable auto-commit** (AI writing would shatter a session into dozens of meaningless commits).
- Git commits double as the vault's **snapshots/undo**: Vault Operator's shadow snapshots only cover writes through Obsidian; external AI writes are only covered by git — when in doubt, commit more.
- Governance files (`CLAUDE.md`, `.claude/settings.json`, `.mcp.json`, `.obsidian-agent*`) are version-controlled; `git log` audits any changes to them.

## 2. Directory map & content model

### 2.1 Top-level structure & permissions

```
my-vault/
├── 00-System/    governance: templates, boards, scripts  AI read-only
├── 01-Inbox/     single entry point, cleared weekly      AI writable
├── 02-Areas/     long-term areas (your judgments)        AI read-only
├── 03-Projects/  active projects (co-writing zone)       AI write-limited (see §2.2)
├── 04-Resources/ clippings originals + voice reference   AI read-only
├── 05-Archive/   archive                                 AI read-only
├── _INDEX.md     entry point
├── CLAUDE.md     AI constitution (read first every session)
└── AGENTS.md     points to CLAUDE.md
```

### 2.2 Project zones (`03-Projects/<project>/`)

| Directory | What lives there | AI permission |
|---|---|---|
| `10-source/` | clippings, interviews, sparks | **read-only** (append-only, maintained by you) |
| `20-notes/` | summary / claim / case cards | read-write |
| `30-drafts/` | v1/ v2/ versions + `_baseline/` | read-write |
| `40-review/` | the version you are editing | read-only |
| `50-final/` | finals | **write-forbidden** |
| `60-published/` | distributed copies | write-forbidden |

Numeric prefixes = flow direction: 10 sources → 20 notes → 30 drafts → 40 review → 50 final → 60 published.

### 2.3 Three-layer content model (where a piece of content goes)

| Layer | Location | What lives there | Who writes |
|---|---|---|---|
| **Originals** | `04-Resources/clippings/` | Third-party articles, verbatim | You (`/intake/clip` stages) |
| **Judgments** | `02-Areas/<area>/` | Your conclusions ("I" statements, still valid in 2 years) | Human only (`/knowledge/note` stages) |
| **Project sources** | `03-Projects/<p>/10-source/` | Material for the current project | You only |

One line to remember: **Projects produce works (for others), Clippings hold others' originals, Areas hold my judgments.**
Typical flow: save an article to clippings → after reading, write your judgment into Areas (linking back) → at the next project kickoff the AI reads your judgments as writing background → conclusions flow back to Areas when the project archives.

## 3. Four core rules

### 3.1 State machine (shared agreement on "where are we")

```
idea → outline → drafting → revising → review → final → published → archived
spark   outline   AI drafts    human edits   fact-check  final   distributed  archived
```

The state lives in each output file's frontmatter `status`. Boards group by it; dragging a card changes it.

### 3.2 Version rules: new version, new file — never overwrite

- AI writes v1 → you copy to `40-review/` and edit → when the AI iterates, it writes `30-drafts/v2/`; **v1 stays untouched**.
- Every AI draft **must** be double-written with an untouched copy in `30-drafts/_baseline/` — the only basis for after-the-fact diffs and quantifying human vs. AI contribution.

### 3.3 AI participation labels (every output)

```yaml
authored_by: ai-assisted   # human | ai-assisted | ai-generated
ai_level: copilot          # none | hint | assist | pair | copilot | auto
ai_model: gpt-5
```

Use: the "AI audit" board surfaces high-AI-participation content for prioritized fact-checking.

### 3.4 human_locked (field-level lock)

Add `human_locked: true` to notes you personally take over — the AI may only **propose** edits. Mandatory for anything entering `50-final/`.

## 4. Daily workflows (by scenario)

### 4.1 Capture (anytime)

Anything — ideas, links — goes into `01-Inbox/`, **unclassified**. Say `/intake/collect <content>` to the AI, or drop files in yourself. Classification happens at the weekly triage (keep capture friction low).

### 4.2 Saving third-party articles (anytime)

1. Found a good article → `/intake/clip <URL or local file>`: the AI fetches the full text **verbatim** into an Inbox staging file (no rewriting/abridging/summarizing); you drag it into `04-Resources/clippings/` (wikilinks follow).
2. After reading, formed an opinion → `/knowledge/note <area> <my judgment>`: the judgment (not an excerpt) is staged into Inbox + a paste-ready `_context.md` delta is generated; you review and land it in Areas.
3. The dividing line: **the article itself only ever lives in clippings; your agreement/disagreement goes to Areas and links back**.
4. Privacy: interviewees, unpublished data, and others' manuscripts never pass through cloud models.

### 4.3 Weekly triage (5–10 minutes)

Run `/intake/triage`: the AI analyzes each Inbox item and proposes a plan; you confirm and execute. Three destinations:
1. Relevant to an active project → into `03-Projects/<p>/10-source/` (the AI can add frontmatter inside Inbox first; you do the move);
2. Area-related → originals into `04-Resources/clippings/`; judgments via `/knowledge/note` into `02-Areas/<area>/`;
3. No value → delete (deletion is always human — rm is denied for AI).

### 4.4 Starting a new project (checklist)

**Step 1 — scaffold**, three options:
- Ask the AI to run `/produce/new your-topic` (script scaffold + AI-filled brief draft + verified paste-ready rows);
- Run the script directly (no AI session needed): `bash 00-System/scripts/new-project.sh your-topic [mini]`;
- Manually copy the demo project and rename.

**Step 2 — write `_brief.md`** (the highest-leverage step): fill in all 11 sections. Cross-area topics use `area: [side-hustle, education]` soft links — **never** copy a project into area folders.

**Step 3 — create `challenges.md` and `journal.md`**: put the strongest arguments against your project in challenges (prevents the AI from just agreeing with you); journal records "done / learned / next".

**Step 4 — index**: add a row in [[_INDEX]] under "Active projects"; add a link under the related area's `_context.md` → "Related projects". (The script or `/produce/new` prints these paste-ready rows.)

**Step 5 (optional)**: bookmark `_brief.md` to pin the topic in the sidebar.

### 4.5 Gathering project sources (append-only, human only)

- Naming: `date-source-title.md` (e.g. `2026-09-06-x-official-blog.md`).
- For manual capture, insert the `tpl-source` template via the Templates plugin (command palette → Insert template).
- Frontmatter keeps `source:` (original URL) and `captured:` (time).
- Excerpts use two blocks: original inside `>` quotes **never modified**, your annotations below.
- **Never let the AI "polish" sources in place** — polished versions go to `20-notes/`.
- Interviewees and unpublished data never go to cloud models.

### 4.6 AI processing into note cards

`/produce/digest <project>`: reads `10-source/`, produces summary/claim/case cards into `20-notes/` (fields per `tpl-note-card`), **each card linking back to its source**.

### 4.7 Co-writing a first draft

`/produce/draft <project> <label>`: the AI reads `_brief.md` + `challenges.md` → drafts into `30-drafts/v1/` based on `20-notes/` → double-writes `_baseline/`. You never re-explain the background — it lives in the brief.

### 4.8 Human editing (AI steps out)

Copy the draft to `40-review/`, set `status: revising`, and add `human_locked: true`. This zone is AI read-only. After major edits, have the AI analyze your patterns (§4.11).

### 4.9 Finalize & distribute

1. Move the final into `50-final/`: `status: final`, `human_locked: true`.
2. After publishing to platforms, copy into `60-published/`, `status: published`.
3. Record one blocker & lesson in `journal.md`.

### 4.10 Archiving a project

`/produce/archive <project>`: pre-checks → the script flips `status` and moves the directory into `05-Archive/<year>/` → the AI distills 2–3 long-term conclusions from journal into paste-ready Areas content. Without an AI session, run `bash 00-System/scripts/archive-project.sh <project>` directly and do the distillation in a session later. **Writing conclusions back is the core value of archiving (the flywheel) — don't skip it** (the "return" in §4.12).

### 4.11 Voice library iteration (gets better with use)

After major human edits run `/quality/voice`: the AI diffs `_baseline/` vs `40-review/`, distills your editing patterns ("he deletes flowery metaphors", "he always adds first-hand observations") into `20-notes/voice-update-<date>.md`, and **you review and merge** into [[04-Resources/voice-reference|voice-reference]]. A style guide grown from real editing evidence beats writing "casual tone" in a prompt.

### 4.12 Area cognition updates (write / revise / return)

> Principle: **cognition updates are triggered by practice, not by the calendar.** There is no "periodic knowledge maintenance" ritual — update affected judgments whenever practice produces new evidence. A judgment untouched for a long time simply hasn't been falsified yet, which is itself information.

| Rule | Trigger | Action |
|---|---|---|
| **write** | a judgment occurs to you | record it: `/knowledge/note <area> <judgment>` (Inbox staging + paste-ready `_context` delta; human lands it) |
| **revise** | it proves wrong in use | fix it on the spot, **as a changelog, not an overwrite**: `/knowledge/note revise <note path>` (AI drafts the revision) |
| **return** | project archive | `/produce/archive` forces distilling 2–3 conclusions back (built into the flow, not optional) |

Revision record format (appended inside the judgment note, preserving evolution and evidence size):

```
2026-09 original: checklist-style headlines get ~2x open rate (n=6, official account)
2027-03 revision: the effect decays; rotate headline patterns (cumulative n=18)
```

Companion rules: `_context.md` is a ≤500-word compressed entry — adding a line means considering dropping one; the AI is read-only on Areas throughout — it can quote, propose revisions, and flag staleness, but the pen is always human.

## 5. Connecting AI tools & the command map

### 5.1 What happens when an AI enters (either way)

```
reads CLAUDE.md (constitution + permissions + routing)
  → your question hits the routing table → reads 02-Areas/<area>/_context.md
  → creative work → reads 03-Projects/<p>/_brief.md + challenges.md
  → only then starts working
```

### 5.2 Primary method: external AI tools + MCP (Claude Code / Codex CLI, etc.)

Everything architectural lives on this path: the constitution and slash commands auto-load; and the **hardest boundary (L1: writes pinned to `03-Projects/`) exists only here** — no Obsidian plugin has an equivalent.

`.mcp.json` ships with two instances, auto-loaded when you **start at the vault root**:

```bash
cd /path/to/your/vault
claude
```

| Instance | Scope | Permission |
|---|---|---|
| `vault-read` | whole vault | read-only retrieval (use this for knowledge-input scenarios) |
| `project-rw` | pinned to `03-Projects/` | writable (for co-writing) |

- First launch asks to approve the two MCP servers — accept; the first npx run downloads packages, allow a moment.
- Second layer: `.claude/settings.json` deny rules block writes to `10-source/`, `40-review/`, `50-final/`, `02-Areas/`, etc. (deny → ask → allow; deny wins).
- Third layer: with Vault Operator installed, `.obsidian-agentprotected` rejects **writes going through Obsidian/its interfaces** (in-vault AI plugins) even with explicit approval. Note the boundary: it cannot see direct writes by external tools — that path relies on the layers above.
- **Working posture**: terminal and Obsidian side by side — you read and edit in Obsidian (`40-review/`), you talk to the AI in the terminal. The zone design guarantees the AI writes `30-drafts/` while you write `40-review/` — never the same file; Obsidian picks up external changes automatically.

### 5.3 Optional enhancement: Claudian (in-Obsidian AI)

It provides **writing feel, not capability**: word-level inline diffs, Plan Mode (`Shift+Tab`), `@`-mentioning vault files — the human-AI loop in one window. It loads the same `CLAUDE.md`, `.claude/settings.json` (deny applies) and all slash commands.

Two known shortcomings: its cwd is fixed at the vault root — **no MCP subdirectory pinning** (the hard boundary stays with external MCP); and it requires Obsidian to be running.

**Whether to install comes down to one question**: do you mind switching windows between the terminal and Obsidian while editing? Suggestion: run two weeks with external tools only; if window-switching annoys you, enable Claudian — the two coexist without conflict.

### 5.4 Other AI tools as knowledge input (read-only)

Any MCP-capable tool (Cursor, Codex, …) only needs the `vault-read` instance — copy that block from `.mcp.json` into the tool's MCP config.

### 5.5 Command map (grouped by function, mirrors `.claude/commands/`)

| Group | Command | Purpose | When |
|---|---|---|---|
| **Intake** `/intake/` | `/intake/collect` | ideas/links into Inbox | anytime |
| | `/intake/clip` | third-party article staging → clippings | anytime |
| | `/intake/triage` | weekly Inbox triage | weekly |
| **Produce** `/produce/` | `/produce/new` | project scaffold + brief draft | kickoff |
| | `/produce/digest` | sources → note cards | after gathering |
| | `/produce/draft` | co-write a draft (double-write `_baseline`) | each round |
| | `/produce/iterate` | next version per human intent | after human edits |
| | `/produce/brief` | brief §9 progress snapshot | weekly |
| | `/produce/archive` | archive + conclusions write-back | project end |
| **Knowledge** `/knowledge/` | `/knowledge/note` | area judgment write / revise | after reading / when stale |
| **Quality** `/quality/` | `/quality/factcheck` | three-tier fact tracing | after drafting |
| | `/quality/voice` | editing-pattern analysis → voice library | after major edits |
| **Query** `/query/` | `/query/search` | vault-wide search (via routing) | anytime |
| | `/query/status` | status overview + staleness | weekly / before work |

> **Two implementations behind the commands**: deterministic operations (mkdir, moves, stats, field flips) are done by bash scripts in `00-System/scripts/` — zero hallucination, zero tokens, runnable without an AI session (`bash 00-System/scripts/status.sh`); judgment operations (writing, analysis, triage) are prompt commands. Hybrid commands = script does the work + AI interprets: `/query/status` (status.sh), `/produce/new` (new-project.sh), `/produce/archive` (archive-project.sh). `.gitattributes` forces LF for `*.sh` so they run on Windows and Linux alike.

**Five functional flows (scenario chains)**:

- **Collect flow**: `/intake/clip` → after reading → `/knowledge/note`
- **Weekly flow** (~10 min): `/query/status` → `/intake/triage` → `/produce/brief` → manual git commit
- **Co-writing flow**: `/produce/draft` → human edits in `40-review/` → `/produce/iterate` → `/quality/factcheck` → final in `50-final/` → (if major edits: `/quality/voice`)
- **Project lifecycle**: `/produce/new` → `/produce/digest` → co-writing flow ×N → `/produce/archive` → conclusions back to Areas
- **Knowledge flow** (goal ②, read-only): any MCP tool with vault-read → `/query/search`

**Four human-AI operating modes** (how "every operation is done or assisted by AI" works):

0. **Script execution** (pure mechanics): mkdir, moves, stats, field flips — `00-System/scripts/`, zero hallucination, no session needed;
1. **Direct write** (AI-writable zones): Inbox, 20-notes, 30-drafts;
2. **Staging** (content landing in AI-read-only zones): Areas, clippings — the AI stages finished content in Inbox + paste-ready deltas; the human drags and pastes;
3. **Advice** (destructive/governance actions): deletion, index changes, permission tweaks — the AI drafts the plan, the human decides.

Forever human: **hard deletes** (rm denied for AI), **governance files** (the AI cannot edit its own shackles), **landing into the trust layer** (final writes to Areas/clippings).

### 5.6 Appendix: equivalent prompts without slash commands

**Sources → note cards:**
> Read `03-Projects/demo-noteai-course/_brief.md`, then process everything under `10-source/`: for each item produce one summary card in `20-notes/`, frontmatter per tpl-note-card, each card ending with a link back to its source. Never modify any file in 10-source/.

**First draft:**
> Read `_brief.md` and `challenges.md`; based on the note cards in `20-notes/`, write "Lesson 3" into `30-drafts/v1/`, and simultaneously save an untouched copy with the same name in `30-drafts/_baseline/`. Frontmatter: status: drafting, authored_by: ai-generated, ai_level: copilot. Address the counter-arguments in challenges.md head-on.

**Iterate:**
> Compare `40-review/lesson-3.md` with `30-drafts/_baseline/lesson-3.md`; once you understand my editing intent, write v2 into `30-drafts/v2/` — leave v1 untouched.

**Analyze my editing patterns:**
> Diff `30-drafts/_baseline/lesson-3.md` and `40-review/lesson-3.md`; distill my editing habits (what I delete, what I add, sentence preferences) into `20-notes/voice-update-2026-09-12.md` for merging into voice-reference. Do not touch 04-Resources/.

**Fact-check:**
> Check every data point, fact, and case in `30-drafts/v2/lesson-3.md`; mark whether each traces to a specific `10-source/` file; output a three-tier checklist (traceable / untraceable / uncertain). Never fabricate sources.

**Knowledge retrieval (read-only):**
> Using vault-read, search the whole vault and summarize everything I have on "compounding", with source links.

## 8. FAQ & pitfalls

**Q: The AI says it can't write a file?**
By design. Check three places: the deny list in `.claude/settings.json`, `.obsidian-agentprotected`, and whether the path is outside the `project-rw` boundary.

**Q: An article is both area reference material and current project material — where does it go?**
Into `04-Resources/clippings/`, referenced from the project via wikilink; only if the project needs to **rewrite** the excerpt, copy it into `10-source/`. Avoid two drifting copies.

**Q: Can I work with external AI tools only, without opening Obsidian?**
At the file level, yes (AI reads/writes via MCP without Obsidian). But boards, wikilinks, templates, and your editing experience in `40-review/` all live in Obsidian — keep it open while writing; it picks up external changes automatically (§5.2).

**Q: Is the AI enforcement absolute?**
No. Layer by layer: on the external path the hard boundary is **only** the MCP vault-root pin; settings deny cannot stop Python/Node scripts opening files directly; Vault Operator only covers writes through Obsidian (its shadow snapshots empirically record no external writes). So sensitive material should never enter AI context in the first place; the undo for external writes is git — one commit per co-writing round.

**Q: Moving the vault to another drive/machine?**
Same platform: update only the vault absolute paths in `.mcp.json` (`.claude/settings.json` is all relative). Or simply re-run `bash init-vault.sh`.
To **Linux/macOS**: the `cmd /c` wrapper is Windows-only — overwrite `.mcp.json` with `.mcp.linux.json` (paths are generated by `init-vault.sh`). Prerequisite: the vault is cloned/synced to that machine; the MCP server must read the files locally.

**Pitfall 1: putting creation projects inside `02-Areas/`** → the write boundary collapses. Projects live in `03-Projects/`, always.
**Pitfall 2: letting the AI polish `10-source/` material in place** → originality is lost irreversibly. Polished versions go to `20-notes/`.
**Pitfall 3: Obsidian Git auto-commit** → one co-writing session shatters into dozens of commits and may clash with unsaved edits.
**Pitfall 4: writing `_brief.md` without `challenges.md`** → the AI agrees with everything; output is flat and tensionless.
**Pitfall 5: tweaking prompts for a better first draft instead of maintaining `_brief.md`** → backwards. Context documents are the asset; text is replaceable.
**Pitfall 6: writing area judgments onto collected originals** → judgments go to Areas (`/knowledge/note`); originals stay pristine, linked both ways.
**Pitfall 7: Obsidian Git on mobile** → officially "highly unstable". Use a sync drive instead.
**Pitfall 8: writing permission rules as `Write(path)`** → officially "accepted but never consulted" — a no-op. Use `Edit(path)`.

## 9. Customizing

### 9.1 Adding an area

1. Create `02-Areas/<area>/_context.md` (copy an existing one; change `area` and keywords).
2. Add a row to the routing table in `CLAUDE.md` (inside the `area-rows` markers). Done.
   (Or re-run `bash init-vault.sh --areas "A,B,C"` — it regenerates areas, the routing table, and `_INDEX.md`.)

### 9.2 Adjusting AI permissions

Edit `.claude/settings.json` (rules use `Edit(path)`, evaluated deny → ask → allow); visibility in `.obsidian-agentignore`, read-but-never-write in `.obsidian-agentprotected`. Commit after changes.

### 9.3 Adding commands & scripts

- **Commands**: copy any `.md` in `.claude/commands/<group>/` and adapt — frontmatter `description` drives when the AI suggests it, `argument-hint` documents parameters. New commands appear in the `/` menu after a session restart.
- **Scripts**: the test — **a step whose correctness can be verified without understanding meaning** (mkdir, moves, stats, field flips) belongs in a bash script under `00-System/scripts/`, called by the command prompt rather than done by hand. `.gitattributes` forces LF for `*.sh`; start new scripts with `#!/usr/bin/env bash` for cross-platform runs.

### 9.4 The demo project

`03-Projects/demo-noteai-course/` is a full example: keep it for reference, copy-rename it as your first real project, or delete it.
